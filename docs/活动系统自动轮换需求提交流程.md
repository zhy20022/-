# 活动系统自动轮换需求提交流程

## 📋 当前实现状态

### ✅ 已完成的功能
1. **活动轮换逻辑** - `EventRotationManager` 类已实现
   - 团队月度活动轮换（每月切换）
   - 全服季度活动轮换（每季度切换）
   - 可以计算当前应该显示的活动
   - 可以计算下次刷新时间

2. **API 接口** - `/api/events/active`
   - 返回当前活动信息
   - 返回下次刷新时间

3. **前端展示** - `ShopPage.tsx`
   - 显示当前活动信息
   - 显示活动商店物品

### ❌ 缺失的功能
1. **自动轮换机制**
   - 活动到期时不会自动切换到下一个活动
   - 需要手动刷新才能看到新活动
   - 没有定时任务或后台检查机制

2. **前端自动刷新**
   - 前端不会自动检测活动是否已切换
   - 需要用户手动刷新页面

3. **活动切换通知**
   - 活动切换时没有通知玩家
   - 没有活动切换历史记录

### 1. 轮换触发方式 ⚠️ **必须明确**

**问题：** 活动到期时，如何触发自动轮换？

**选项：**
- **A. 定时任务（推荐）**
  - 使用后台定时任务（如 Celery、APScheduler）
  - 每分钟或每5分钟检查一次活动是否到期
  - 到期时自动切换到下一个活动
  
- **B. 请求时检查**
  - 每次有用户请求活动信息时检查
  - 如果发现活动已到期，自动切换
  - 优点：简单，不需要额外服务
  - 缺点：如果长时间没人访问，活动不会自动切换

- **C. 混合方式**
  - 定时任务 + 请求时检查
  - 定时任务负责主要轮换
  - 请求时检查作为补充

**请选择：** A / B / C

### 3. 前端自动刷新 ⚠️ **必须明确**

**问题：** 前端是否需要自动检测活动切换？

**选项：**
- **A. 自动轮询**
  - 前端每 X 分钟自动请求一次活动信息
  - 检测到活动切换时，自动更新界面
  - 优点：用户体验好，无需手动刷新
  - 缺点：增加服务器请求次数
  
- **B. WebSocket 推送**
  - 活动切换时，服务器通过 WebSocket 推送通知
  - 前端收到通知后自动更新界面
  - 优点：实时性好，减少请求
  - 缺点：需要 WebSocket 连接
  
- **C. 页面可见时检查**
  - 当用户切换到活动页面时，自动检查活动是否已切换
  - 如果切换了，自动更新界面
  - 优点：简单，不增加额外请求
  - 缺点：需要用户主动访问页面

- **D. 不自动刷新**
  - 用户需要手动刷新页面才能看到新活动
  - 优点：最简单
  - 缺点：用户体验较差

**请选择：** A / B / C / D

**如果选择 A，请提供轮询间隔：**
- 轮询间隔：__ 分钟（建议 1-5 分钟）
