## 📋 如何给我提需求

### 方式一：结构化需求（推荐）

按照以下格式提供需求，我会更容易理解和实现：

```
【功能名称】
背景/目的：为什么需要这个功能
触发流程：什么时候、如何触发
展示内容：需要显示什么信息
交互逻辑：用户如何操作
技术范围：需要改后端、前端、还是数据库
数据来源：数据从哪里来
验收标准：怎么算完成
```

**示例：**
```
【副本掉落展示】
背景/目的：让玩家看到自己和队友的掉落
触发流程：战斗时实时显示，结算时详细展示
展示内容：物品名称、数量、品质、来源玩家
交互逻辑：分页、过滤、排序、点击查看详情
技术范围：后端接口、前端页面、WebSocket推送
数据来源：战斗系统的reward_config
验收标准：能正确显示所有掉落，支持过滤和排序
```

---

### 方式二：分步骤需求

如果功能复杂，可以分步骤提：

1. **第一步：基础功能**
   - 描述最核心的功能
   - 我实现后，你测试反馈

2. **第二步：扩展功能**
   - 在第一步基础上添加功能
   - 逐步完善

3. **第三步：优化和细节**
   - UI优化
   - 性能优化
   - 细节完善

---

### 方式三：参考游戏需求

如果参考其他游戏，可以这样提：

```
【功能名称】
参考游戏：XXX游戏
核心玩法：描述核心玩法
需要实现：列出需要实现的功能点
不需要实现：列出不需要的功能（避免误解）
特殊要求：如果有特殊要求，单独说明
```

**示例：**
```
【好友系统】
参考游戏：失落的龙约
核心玩法：无限好友、助战奖励
需要实现：
- 好友列表（无上限）
- 助战开关
- 助战奖励（开启时掉落货币）
不需要实现：
- 好友申请/审批流程
- 好友聊天
特殊要求：
- 助战奖励每次掉落1000通用货币
```

1. **尽量具体**：避免"做一个XX系统"这种模糊需求，尽量描述具体功能点
2. **分步骤**：复杂功能可以分步骤，我先实现核心功能，你再提扩展需求
3. **提供参考**：如果参考其他游戏，说明参考哪些点，哪些不需要
4. **明确范围**：说明需要改哪些部分（后端/前端/数据库），避免我误解
5. **验收标准**：说明怎么算完成，避免理解偏差
